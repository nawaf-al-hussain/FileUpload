### 3.2 Request behavior verified from code (all [OBSERVED] this phase)

- **All asset URLs are relative and same-origin.** Loader: `REMOTE_PACKAGE_BASE = 'reVC.data.b33'`, plain `fetch(packageName)` (`reVC_data_b33.js` lines 22–38). Page seeding: `fetch('gta3.img')` (index.html line 174). Worker fallback: sync XHR `responseType:"blob"` to the relative URL (`reVC.js` lines 1472–1486). WASM resolves from `scriptDirectory` (page directory).
- **No OPTIONS/preflight, no CORS, no custom request headers anywhere in the runtime.** `setRequestHeader` occurs exactly **once** across all three JS artifacts — inside emscripten's `createLazyFile` byte-serving path (`reVC.js` line 4709, `Range` header) — which is **present but unused** for our assets. Range support in the hosting chain is therefore a **diagnostic/robustness property, not a current runtime requirement** (re-confirmed; matches Phase 8A §2.3).
- **OPFS resume semantics**: per-part exact-size check on load (`st.size !== want → have=false → full re-seed`, index.html ~lines 167–171); writers truncate; no byte-range resume of an interrupted seed; fetch failure → blob fallback this session. Hosting-independent.
- **Worker delivery**: page Worker-constructor hook posts `{b33opfsParts,…}` + 250 ms idempotent re-broadcast (index.html lines 137–156); workers open `createSyncAccessHandle()` per part; glue side carries the B3.4 self-serve/idempotent blocks (`b34_pre.js` content, committed) — verified in the glue this phase.
- `sendBeacon('/log')` may 404 harmlessly [OBSERVED line 36].

### 3.5 Verified facts vs untested — hosting

**Verified facts (provider docs, re-fetched and quoted today):**

- Vercel static upload limit **100 MB (Hobby) / 1 GB (Pro)** per source file — "If the size of the source files exceeds this limit, the deployment will fail" ⇒ both 175 MB and 327 MB files **cannot** ship in a Hobby deployment [vercel.com/docs/limits, fetched 2026-10-18].
- Vercel proxied-request timeout **max 120 s on all plans** for `rewrites`/external-destination routes [same page, fetched 2026-10-18].
- R2 public access via **custom domain** supported; `r2.dev` is "rate-limited and should only be used for development purposes"; CNAME-to-`r2.dev` explicitly **unsupported**; "For production use, add your domain to Cloudflare" [developers.cloudflare.com/r2/buckets/public-buckets, fetched 2026-10-18].
- Carried from Phase 8A (sourced there): R2 5 TiB/object, free egress, 10 GB free storage; GH Releases 2 GiB/file, unlimited release size/bandwidth; GH Releases assets **cannot be read cross-origin by browser JS** (measured: no ACAO on either redirect leg, Phase 8A §2.2) ⇒ Releases are canonical **storage**, never the browser origin; external rewrites = reverse proxy, upstream `cache-control` honored [vercel.com/docs/routing/rewrites + KB guide].

**Repo-side facts [OBSERVED]:**

- All five runtime files are git-ignored (`.gitignore` lines 32–36, "must never enter git") ⇒ a deployment built from the repo alone serves **only** `index.html` under `/revc/` — everything else 404s. Any A1 implementation must proxy **all five** files (the Phase 8A-corrected scope; the Phase 7 original plan covered only the two big files).

**Untested (nothing this phase can verify without a real deployment — the go-live gates):**

1. **Rewrite passthrough fidelity**: exact preservation of status 200, `Content-Length`, `Content-Type` (esp. `application/wasm`), `Cache-Control` from R2 object metadata, and behavior for ~500 MB bodies through Vercel's edge. Not documented by Vercel; must be measured on a disposable preview.
2. **Cold vs warm + slow clients vs the 120 s timer**: whether a cold proxied fetch of 327 MB aborts for slow clients (needs > ~2.7 MB/s to fit 120 s [ESTIMATE: 327,487,488 B ÷ 120 s]); whether warm edge-cache hits bypass the upstream timer (standard CDN behavior — **inference, not documented guarantee**).
3. **R2 object metadata correctness in practice** (`Content-Type`/`Cache-Control` actually emitted by the custom domain).
4. Whether Vercel follows an upstream redirect (A1 avoids this entirely by pointing rewrites at the R2 custom domain directly — no redirect in chain — but it belongs on the checklist if the origin is ever changed).

## 6. Explicit decision criteria — A1 vs the C1 fallback (Vercel Pro all-in-deployment)

**Choose A1 (Vercel Hobby + R2 custom-domain proxy) if ALL of:**

1. Gate A passes: 200 + exact `Content-Length` + correct `Content-Type` + `immutable` cache headers on all five files on both mounts; full-body hashes match (5/5).
2. Gate C passes: OPFS path, blob-fallback path, `crossOriginIsolated`, homepage regression, keyboard regression — all green.
3. Gate B outcome is one of: warm-cache throttled downloads complete (cold-cache abort acceptable **only** with the documented mitigations — warm the edge cache after each asset version bump, restrict early usage to testers — and recorded as a known limitation), or throttling is simply not exercised by realistic client speeds.

**Escalate to C1 (Vercel Pro, all seven files in-deployment, no proxy, build-time fetch from the canonical release) if ANY of:**

1. Gate A fails on hash, length, or `Content-Type` for any file (byte fidelity cannot be achieved through the proxy).
2. Warm-cache throttled downloads abort mid-stream (slow clients can never finish asset delivery on the proxy path).
3. The user's Cloudflare prerequisite proves unresolvable (no zone/domain obtainable) — C1 needs only Vercel Pro + the GH-release download secret.
4. Real-traffic transfer overage on Hobby becomes unacceptable (C1 moves delivery to Vercel Pro's pricing without the proxy hop).

**Cost frame for the decision** [ESTIMATE, sourced unit prices in Phase 8A §6]: A1 ≈ $0 at validation scale (R2 free tier; egress free; Hobby 100 GB/mo ≈ 200 cold first-visits); C1 = $20/mo Vercel Pro + transfer, plus one read-only release-download secret in the build.

**Explicitly not alternatives** (Phase 8A §4, evidence stands): GitHub Releases as browser origin (measured: no CORS), `r2.dev` as production origin (Cloudflare: unsupported/rate-limited), GH Pages (no COOP/COEP), CF Pages (25 MiB/file), B2 (dominated by R2 egress).
